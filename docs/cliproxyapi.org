#+TITLE: CLIProxyAPI

* CLIProxyAPI on Kit
CLIProxyAPI runs alongside codex-lb. Existing clients keep using codex-lb until explicitly changed. The API base URL is =https://cliproxyapi.kit/v1=; the management panel is =https://cliproxyapi.kit/management.html=. Traefik restricts both to LAN and Tailscale clients. The backend listens only on =127.0.0.1:8317=, with no direct firewall opening.

The local module is copied from [[https://github.com/NixOS/nixpkgs/blob/fe13242281a67641c0102cdb1087f0ebe586c7df/nixos/modules/services/misc/cliproxyapi.nix][pinned unstable nixpkgs]] and disables =services/misc/cliproxyapi.nix= before declaring its options. It uses =pkgs.unstable.cliproxyapi= without importing the rest of unstable's NixOS modules.

** Before first activation
Provision two separate keys in Kit's persistent backing directory. These are client API and management keys, not provider credentials. The commands skip existing files and refuse to overwrite a file created concurrently. Run from a shell with =openssl= available, such as =nix shell nixpkgs#openssl=.

#+begin_src sh
state=/mnt/main/storage/var/lib/cliproxyapi
sudo install -d -m 0700 "$state"
for key in api-key management-key; do
  if ! sudo test -e "$state/$key"; then
    openssl rand -hex 32 | sudo sh -c 'umask 077; set -C; cat > "$1"' sh "$state/$key"
  fi
done
#+end_src

Activate Kit through the normal deployment workflow when ready. Impermanence mounts that directory at =/var/lib/cliproxyapi= and sets its owner to =cliproxyapi:cliproxyapi=. Systemd loads the key files as credentials before generating =config.yaml=. Missing keys prevent startup. OAuth tokens and keys are covered by storage snapshots and backups; nothing secret belongs in Git or the Nix store.

Retrieve the keys locally when adding clients or opening the management panel:

#+begin_src sh
sudo cat /var/lib/cliproxyapi/api-key
sudo cat /var/lib/cliproxyapi/management-key
#+end_src

** Add subscription accounts
While codex-lb runs, add accounts through the CLI as the service user so tokens have the right owner. The panel's Codex login uses the default callback port and can conflict with codex-lb. Repeat the CLI login for each of the four ChatGPT accounts, selecting the intended account in the browser each time. A subscription login uses OAuth, not a platform API key.

Codex normally uses callback port =1455=, which codex-lb already owns. Use another loopback callback port for CLI logins while both services run:

#+begin_src sh
sudo -u cliproxyapi cliproxyapi -config /var/lib/cliproxyapi/config.yaml -codex-login -oauth-callback-port 1456 -no-browser
sudo -u cliproxyapi cliproxyapi -config /var/lib/cliproxyapi/config.yaml -claude-login -no-browser
#+end_src

The CLI prints the authorization URL. Open it in the desired browser session and follow the prompt to paste the redirect URL if needed. Tokens land in =/var/lib/cliproxyapi=; the running daemon watches for new credentials. Browser login callbacks must target Kit, not another machine's localhost. For management-API logins while codex-lb runs, use the non-webui flow and submit the final redirect URL as described in the [[https://github.com/NixOS/nixpkgs/blob/fe13242281a67641c0102cdb1087f0ebe586c7df/nixos/modules/services/misc/cliproxyapi.md][upstream module guide]].

Routing uses round-robin for new sessions and keeps established sessions on the same account when possible. Unavailable credentials fail over. Supporting Claude OAuth does not establish that Anthropic permits using a Pro subscription through third-party clients; check current subscription terms before enrolling that account.

** Policy compared with codex-lb
The module approximates codex-lb's sticky routing, not its quota planner:

- New sessions use equal round-robin. Weighted round-robin in CLIProxyAPI uses static credential weights, not remaining quota, so it is not a replacement for codex-lb's capacity-weighted policy.
- Sessions stay on one account with a =30m= binding TTL. Subagents inherit the parent's credential. This resembles codex-lb's sticky threads and 1800-second prompt-cache window, but the binding TTL does not control OpenAI's cache lifetime.
- Quota or authentication failures rebind a session to another usable credential. Transient failures may fail over for one request without permanently moving the session. Cooldown status is saved beside OAuth files and survives restarts; session bindings are not promised to survive.
- Requests allow three additional credential retry rounds after the first round, considering all available credentials in each round. The cooldown-wait setting is 30 seconds. This is not a three-attempt cap or a 30-second total request deadline.
- Streaming sends keepalive comments every 15 seconds and permits one bootstrap retry before the first byte. It does not replay a partially delivered answer.
- Usage event publication is enabled. The management queue retains events briefly, for 60 seconds by default, rather than storing request history. Upstream removed built-in historical usage statistics in v6.10.0. Debug logging and full request logging remain off.

There is no configured equivalent for codex-lb's 95%-used sticky thresholds, preference for earlier weekly resets, reset-triggered warmups, Spark credit policy, or separate per-account response-create, stream and recovery-reserve limits. Codex-lb's planner was in shadow mode with synthetic traffic disabled, so it was not actively steering requests. No synthetic warmups, model substitutions or payload rewrites are added here.

Both proxies spend the same upstream quota when they use the same ChatGPT account. They do not coordinate sticky routing or cooldown state. Keep both running for comparison, but do not count their account pools as separate capacity. Start a fresh client session when switching proxies; existing sticky bindings and proxy-local state do not transfer.

** Recover a stale cooldown
A manual or early upstream quota reset may leave a credential in local cooldown. Saved cooldowns survive service restarts, so restarting does not clear them. Confirm the account has usable quota before clearing its cooldown.

Use the management key to call =GET /v8/management/credentials= and find the affected credential's =auth_index=. Then call =POST /v8/management/routing/cooldown/reset= with JSON body ={"auth_index":"the-affected-index"}=. This clears the credential's in-memory and saved cooldowns. See [[https://github.com/router-for-me/CLIProxyAPI/issues/5639][upstream issue 5639]] and the [[https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.25/docs/management-api-v8.md][v8 management API guide]].

** Check and use
After login, list models using the separate client API key:

#+begin_src sh
curl --fail-with-body -H "Authorization: Bearer $(sudo cat /var/lib/cliproxyapi/api-key)" https://cliproxyapi.kit/v1/models
systemctl status cliproxyapi.service
journalctl -u cliproxyapi.service -b
#+end_src

Use =https://cliproxyapi.kit/v1= and the client API key in an OpenAI-compatible client. Use model IDs returned by =/v1/models=. No existing client is switched automatically.

Keep durable settings in =services.cliproxyapi.settings=. The module regenerates =config.yaml= at each service start, so management-panel configuration changes do not survive a restart. OAuth token files do survive. Arbitrary secrets can still use upstream's =._secret = "/path/to/file";= syntax; =environmentFile= remains available.
